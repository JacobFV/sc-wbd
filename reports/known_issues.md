# Known issues — data substrate (agent 🗄️ Ada, `scwbd/sources/**`)

Hand-written. Unlike `reports/data_inventory.md`, this file is **not** regenerated by
`python -m scwbd.sources.report`; edit it directly.

Each entry names a defect that is currently *latent* — the system behaves correctly
today, but for a reason that is not guaranteed by any contract. A latent defect in a
system whose premise is "an unknown field stays unknown" is worth writing down before
it becomes an incident.

## ISSUE-001 — `UncertaintyLedger` cannot represent an unknown bias, so "unknown" is encoded as a zero-width interval

**Status:** open. Guarded by a test; needs a schema change to close properly.
**Owner of the fix:** 📜 (schema), sequenced by the coordinator — deliberately *not*
patched mid-flight by 🗄️ Ada.
**Severity:** latent. No live card currently exercises the path (see "Why nothing is
broken today"), so this is a defect in the *contract*, not in today's outputs.

### The defect

`scwbd.schema.UncertaintyLedger.bias_interval` is typed

```python
bias_interval: tuple[float, float] = (0.0, 0.0)
```

It is a required pair of floats. There is **no value of this type that means "we do not
know the bias"**. The YAML source cards *can* say so — they write the literal
`bias_interval: unknown`, and seven cards currently do — but that statement has nowhere
to land in the typed model.

So `SourceCardDoc.to_typed_payload` (`scwbd/sources/cards.py`) does this:

```python
"bias_interval": tuple(led["bias_interval"])
                 if not _is_unknown(led["bias_interval"])
                 else (0.0, 0.0),
"bias_status":   led["bias_status"]
                 if led["bias_status"] != UNKNOWN
                 else "prior_specified_sensitivity",
```

An unknown bias becomes the interval `[0, 0]` — which, read literally, is the strongest
possible claim the field can make: *the systematic error of this source is exactly
zero*. That is the precise inversion the project exists to prevent.

### Why nothing is broken today

Two accidents, not two guarantees:

1. **No live card reaches the branch.** Every card with `bias_interval: unknown` today
   (`adni`, `hcp-young-adult`, `ram-intracranial`, `things-eeg2`, `tuh-eeg`,
   `ukbiobank-brain-imaging`) has `governance.status: unavailable`, and
   `bind_typed()` refuses to project unavailable cards at all. The branch is dead code.
   It stops being dead the moment anyone downloads one of those datasets, or writes a
   live card with an unresolved ledger.

2. **`has_estimator()` happens to catch it.** The fallback is byte-identical to what
   📜's own `UncertaintyLedger.unknown()` constructor emits, and R08 is enforced through

   ```python
   def has_estimator(self) -> bool:
       if self.bias_status == "design_estimable":     return bool(self.bias_estimator)
       if self.bias_status == "externally_bounded":   return bool(self.external_bound_source)
       return not self.is_bias_point_estimate      # <-- the accident
   ```

   For `prior_specified_sensitivity` the check is "the interval is not degenerate".
   A zero-width interval is degenerate, so `has_estimator()` returns False and R08
   refuses the source downstream. The unknown *is* caught — but only because
   "unknown" and "zero" happen to share an encoding that a third predicate happens to
   reject. Nothing states that they must.

This is why the correct description is **safe by accident**. Three independent things
(the projection's choice of `(0.0, 0.0)`, `has_estimator`'s use of
`is_bias_point_estimate`, and the fact that no live card has an unknown ledger) must all
stay true for the system to keep behaving. Any one of them can change without the others
noticing.

### How it would fail

- A legitimate source whose bias genuinely *is* a measured zero — a phantom-anchored
  calibration with `bias_status: design_estimable` and a named estimator — is
  indistinguishable at the type level from a source that knows nothing. Today
  `has_estimator()` separates them via `bias_estimator`; if a future refactor keys
  admissibility off the interval alone, "unknown" silently becomes "verified zero".
- Any consumer that reads `bias_interval` *without* consulting `has_estimator()` —
  a sensitivity sweep, an error-bar renderer, an aggregation across sources — reads a
  confident zero. `bias_width` returns `0.0`, so an unknown source contributes nothing
  to a propagated uncertainty budget instead of dominating it.
- `ARCHITECTURE.md` rule 1 says missing data is never imputed as zero. This is exactly
  that imputation, one level up: not missing *data*, but a missing *reliability claim*.

### Interim guard (in place)

`tests/sources/test_cards.py::test_unknown_bias_never_projects_as_a_zero_bias_claim`
pins accident (2): it builds the payload an unknown-ledger live card would produce and
asserts `is_bias_point_estimate and not has_estimator()`. If `has_estimator` stops
keying off the degenerate interval, that test fails loudly instead of the system
silently starting to read unknowns as zeros.

The guard does **not** fix the defect. It converts a silent failure into a noisy one.

### The proper fix (schema change — not made here)

Give "unknown" its own representation rather than overloading a degenerate interval.
Sketch, for 📜 to take or reject:

```python
bias_interval: tuple[float, float] | None = None   # None == not established
bias_status: BiasStatus | Literal["unknown"] = "unknown"
```

with `has_estimator()` returning False for `None`/`"unknown"` *by definition* rather
than by arithmetic, and any consumer of `bias_width` forced to handle `None`. The
`BiasStatus` literal would gain `"unknown"`, which the YAML cards already use and which
`scwbd/sources/cards.py::VALID_BIAS_STATUS` already accepts — so the card layer is
already ahead of the typed layer here, and closing the gap means moving the typed layer
to match the cards, not weakening the cards to match the types.

Once that lands, delete the `(0.0, 0.0)` fallback in `to_typed_payload` and let the
unknown propagate as an unknown.

### What must NOT be done

Do not "fix" this by giving the cards a numeric bias interval they have not measured.
Six of the seven affected cards are `unavailable` precisely because nobody has the data;
inventing a bound for them would be fabrication. The card layer is correct. The typed
layer is the one that cannot say what the card already says.

## ISSUE-005 — one `Missingness` object per card cannot express two co-occurring mechanisms

**Status:** open (schema expressiveness gap). Worked around in `ds004024.yaml` with a
declared, auditable choice; no schema change made.
**Owner of the fix:** 📜 (schema), if the coordinator judges it worth the churn.
**Severity:** low but recurring — any card describing a *subset of* a larger release
will hit it.

### What happened

`scwbd.schema.Missingness` validly refuses `mechanism="mnar"` with
`handling="drop_episode"`:

> MNAR missingness cannot be handled by masking alone; use a missingness model,
> weighting, or a design factor

That constraint is statistically correct and was **not** weakened. If data are missing
not-at-random, dropping the missing episodes embeds the bias rather than removing it.

But `ds004024` has *two* missingness processes running at once, and the schema gives one
`mechanism`/`handling` pair to describe both:

| | process | mechanism | admissible handling |
|---|---|---|---|
| 1 | our subset choice (2 of 13 subjects, 1 of 3 asynchronies, runs 01-06 of 12) | `planned` — deterministic, ours, fully enumerated | `drop_episode` |
| 2 | upstream session attendance (13/11/7 for 14/4/9 ms; design vs drop-out indistinguishable) | possibly `mnar`, genuinely `unknown` | *not* `drop_episode` |

Declaring `mnar` made the card fail validation. Declaring one of the admissible MNAR
handlings (`missingness_model`, `inverse_probability_weight`, `design_factor`) would
have been a **lie** — no such model exists for this source. Declaring `planned` is true
of the dominant process but silently drops the MNAR risk in the second.

### Resolution taken

`mechanism: planned`, `handling: drop_episode`, plus a ~30-line comment block in the
card naming both processes, plus two card-level fields that do not project
(`upstream_attendance_mechanism: unknown`,
`upstream_attendance_mnar_risk: <prose>`).

The residual MNAR component is **confined, not corrected**: it can only bias a quantity
pooled across participants, and `split_policy.notes` already requires the Fisher-rank
claim to be reported per participant and never pooled. The card now states that this
per-participant rule is *the reason* the MNAR component cannot reach a published number,
and that any consumer who pools across participants must re-derive `mechanism` as
`mnar` and supply an admissible handling rather than reusing the `planned` declaration.

### If it were to be fixed properly

Allow a sequence of missingness processes rather than one:

```python
missingness: tuple[Missingness, ...]     # each with its own mechanism/handling
```

with the card-level rule that the *most adversarial* mechanism present governs what
claims are admissible. That is a wide-blast-radius change to a core schema type for one
card's benefit, which is why it is written down here rather than made. If other agents'
cards hit the same wall — and any card describing a fetched subset of a larger release
will — that is the signal to do it.

## ISSUE-002 — `pgrep -f` guards self-match (fixed here, recorded as a pattern)

**Status:** fixed in `/data/scwbd/ds004024/fetch.sh`; recorded because the pattern is
likely to recur in other agents' fetch/relaunch guards.

A guard of the form

```bash
pgrep -f 'aws s3 sync' && echo ALREADY RUNNING && exit 1
```

matches **its own shell's command line**, because the invoking `bash -c` process has the
literal string `aws s3 sync` in its argv. The guard therefore fires unconditionally and
the job never starts — a false "already running" that is indistinguishable from a real
one. This cost one relaunch cycle here.

Use a lock, not a process-name scan:

```bash
flock -n /path/to/job.lock /path/to/job.sh
```

`flock` is race-free, releases automatically if the holder is killed (including by the
OOM killer), and cannot match itself. Where a process scan is genuinely wanted, match the
script path (`pgrep -f 'ds004024/fetch.sh'`) rather than a substring that the guard
itself contains, and exclude `$$`/`$PPID`.

## ISSUE-003 — interrupted `aws s3 sync` leaves multipart temp files that look like real data

**Status:** fixed in `fetch.sh` (explicit cleanup before each run); recorded because the
failure mode is silent and mis-reads as successful partial download.

When `aws s3 cp/sync` is killed mid-multipart (here: an OOM reboot), it leaves temp files
named `<target-name>.<8 hex digits>` — e.g.
`sub-CON006_ses-async14ms_task-spTMS_run-03_eeg.eeg.E6999C1a`. They are **not** named
`.part`, so a `find -name '*.part'` check reports a clean tree. They also do not resume:
a subsequent `aws s3 sync` ignores them entirely and re-downloads from zero, so they
accumulate.

Here they totalled 1,577,058,304 bytes across 4 files and were the *entire* apparent
contents of `sub-CON006` — a subject that a byte-count-based inventory would have
reported as holding 1.5 GB of signal data while in fact holding none. Had that reached
the register, `sub-CON006` would have become a phantom subject with real metadata and
zero recoverable signal.

Detection and cleanup:

```bash
find "$DST" -type f -regextype posix-extended -regex '.*\.[0-9a-fA-F]{8}$' -delete
```

`fetch.sh` now runs this before syncing and counts survivors afterwards, reporting the
count in its completion sentinel — a nonzero `leftover_tmp` means a transfer did not
finish, regardless of the exit code.

## ISSUE-004 — a completion sentinel must be written by the job, not echoed to a log

**Status:** fixed; recorded as a pattern.

The pre-crash `fetch.sh` ended with `echo "FETCH_DONE $(date -Is)"` to stdout, and a
watcher polled `grep -q FETCH_DONE sync.log`. The job was killed before that line ran,
so the sentinel never existed — `grep -c FETCH_DONE sync.log` was `0` — and the polling
loop was unwinnable regardless of how long it waited. A sentinel that lives in the same
stream as the job's progress output cannot distinguish "not finished" from "died".

The sentinel is now a **file**, written by the script's own last line, carrying the
accumulated exit status and the leftover-temp-file count:

```bash
echo "FETCH_DONE rc=$RC leftover_tmp=$LEFTOVER at=$(date -Is)" > "$SENTINEL"
```

A watcher then has three distinguishable states: sentinel absent + process alive
(running), sentinel absent + process gone (died), sentinel present (finished — and
`rc`/`leftover_tmp` say whether it finished *well*). Verify the sentinel logic before
relying on it: the cheapest check is to confirm the string can appear at all.

## ISSUE-006 — every lead field ever built used a Fibonacci spiral, while its own note said "real 10-10 montage positions"

**Status:** fixed in code 2026-08-07 (`scwbd/foundation/heads.py::_montage_positions`).
**Not fixed in the published run-2 artifact**, which cannot be: the weights are trained.
**Severity:** shipped. This is a description of a released checkpoint, not a latent
contract defect, which is why it is recorded here rather than repaired quietly.

### The defect

`_montage_positions` looked an electrode up like this:

```python
v = lower.get(n.lower()) or lower.get(n.lower().replace(".", ""))
```

`lower.get(...)` returns a length-3 `ndarray` of coordinates. `ndarray or ...`
evaluates the array's truth value, and numpy raises

```
ValueError: The truth value of an array with more than one element is ambiguous.
```

The raise happens on the **first electrode that is found**, not on a missing one — so
the function did not degrade for unusual montages, it failed for every montage,
always, on the first channel. `build_lead_field` wraps the call in

```python
except Exception:  # noqa: BLE001 - mne montage unavailable
```

and falls through to a Fibonacci spiral of points on a sphere. The comment names the
condition it was written for (mne absent) and caught a different one.

All 64 eegmmidb electrodes are present in `standard_1005`. Not one of them was ever
used. Measured after the repair, the same 64-channel operator has condition number
193.8 on real geometry.

### Why nothing reported it

The `LeadField.note` is a literal string, written once at the bottom of the fallback
branch, and it read:

> ...homogeneous conducting sphere with electrodes at real 10-10 montage positions.

There is only one branch that builds the analytic field, so the note describing the
real-geometry case was attached to the synthetic-geometry case. `provenance` said
`analytic_sphere_fallback` truthfully — that names the *sphere*, which was always the
model, not the *electrode positions*, which were the thing substituted. Every audit
that read the provenance string got a true answer to a different question.

### Scope

This changes the operator, so it changes the model. It does **not** invalidate the
orientation result (5.6% scalar vs 51.7% 3-vector): that was measured by 🧲 Gauss on a
real BEM solution, not on this fallback. It does bound anything read off this
operator's *spatial* structure in runs 1 and 2 — the note now states which geometry
was used, and `test_montage_adapter.py` asserts the real path is the one taken.

### The pattern

A fallback whose `except` clause names one cause will silently absorb every other
cause, and a note written inside the fallback branch will describe whatever the author
had in mind rather than what ran. Where a substitution is possible, the artifact must
carry which branch produced it — derived at runtime, not written as a literal. That is
now what `geometry` in `build_lead_field` does.

## ISSUE-007 — `tests/schema/test_carrier_and_views.py` cannot be collected, and takes the whole schema directory with it

**Status:** open. **Not** repaired here: which `support_algebra` is authoritative is a
design call, not a fix.
**Severity:** live. `pytest tests/schema` aborts at collection; without
`--continue-on-collection-errors` the other 229 schema and foundation tests in the same
invocation do not run.

### The defect

`wt/noether2` and master independently added `scwbd/schema/support_algebra.py` as two
different implementations of the same idea with different public names:

| master | noether2 |
| --- | --- |
| `relate` | `restriction_between` |
| `compose_psf` | `_compose_psf` |
| `common_temporal_refinement` | `common_refinement`, `temporal_common_refinement` |
| — | `element_join`, `embed_along`, `project_along` |

The merge kept master's, because `tests/schema/test_support_algebra.py` imports it.
Everything else from that branch was additive and landed — **including
`tests/schema/test_carrier_and_views.py`, which imports noether2's six names.** So a
test file from one implementation now sits beside the other implementation, and the
import fails at collection time rather than as a test failure.

HANDOFF-003 records that master's `support_algebra` was kept and that
`test_carrier_and_views.py` landed. It does not record that those two facts contradict
each other, which is why this is written down here.

### Why it is not repaired here

The signatures differ, not just the names: `common_refinement(a, b, ia, ib,
atom_weights=...)` has no counterpart in master's API. Porting means choosing which
implementation of the support algebra is authoritative and rewriting the other's tests
against it. That is the same category as the R12 duplication (`R12Violation` vs
`CompilerRefusal`) which the handoff also declines to repair: a design decision with two
defensible answers, made worse by being taken in passing.

### What would discharge it

Decide which implementation is authoritative. If master's: rewrite
`test_carrier_and_views.py` against `relate` / `compose_psf` /
`common_temporal_refinement`, and port `element_join`, `embed_along` and `project_along`
if the carrier work needs them. If noether2's: replace the module and rewrite
`test_support_algebra.py`. Either way one test file gets rewritten; the current state is
the only one where neither does and the directory does not run.

### The pattern

A merge that keeps one side of a conflicted *module* must also decide what happens to
the other side's *tests*, and "everything else was additive" is not the same as
"everything else is consistent". An additive file that imports the rejected API is a
collection error, which is louder than a failure and easier to mistake for an
environment problem.
